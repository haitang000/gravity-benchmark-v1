# GravityBench 2B–14B 题目设计原则

## 目标

首版题目用于比较小型模型的稳定执行能力，不用长篇知识问答替代能力测试。每题都尽量让“输出格式”与“答案正确性”可程序化判定。

## 难度边界

- `easy`：单步变换、短文本、基础算术、一个 Python 函数；适合 2B–4B 模型。
- `medium`：两到三个约束、简单信息抽取、一次代数/比例推理、短函数修复；适合 4B–8B 模型。
- `hard`：多步组合、嵌套结构、边界条件和更复杂代码；只进入 `full`，适合 8B–14B 模型。hard 题保持短输出和确定性答案，测试组合推理与稳定执行，不要求模型生成长篇思维链。

## 统一运行约束

- 指令、数学、编程默认 `temperature=0`。
- 默认 `max_tokens=256`；题目不要求长文章或长思维链。
- 编程题要求只输出代码，测试以 pass@1 为主。
- 数学题优先要求最终答案，避免把语言表达能力混入基础算术分数。
- 中文和英文按相同能力标签配对，报告中分别统计语言分项。
- 题库版本和 SHA-256 写入运行记录，避免题目变化导致结果不可比。

## 推荐解读

- 2B–4B：重点观察 easy 题通过率、格式服从和输出冗余。
- 4B–8B：增加 medium 指令组合、基础代数和列表/字符串编程。
- 8B–14B：可单独启用 hard 扩展，比较多步推理、长上下文和复杂修复。

`core_tasks.json` 保存基础题，`extended_tasks.json` 保存 full 的分层压力题。当前 full 由两者合并后按语言筛选，题目 ID 必须唯一，禁止用重复题目凑样本数。运行接口会返回每套件的类别和难度计数，方便在 WebUI 启动前确认规模。
